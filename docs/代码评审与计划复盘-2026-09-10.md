### 1.2 做得对的地方（具体到行，不是客套）

1. **分层是真正的接口解耦，不是摆设。**
   `llm.Client` / `tool.Tool` 两个接口，`cmd/main.go` 是唯一知道具体实现的装配点。内部包放在 `internal/` 下，靠模块路径阻止外部导入——Go 的标准布局。

2. **adapter 模式落实了。**
   `llm.Message`（对内契约）↔ `chatMessage`（线上格式）在 `Chat` 内转换。换厂商只改 `GLM.go`，agent 内核零改动。设计动机站得住。

3. **HTTP 细节处理得比一般人好。**
   - `NewRequestWithContext` ✓
   - `Do` 之后 `defer resp.Body.Close()` ✓
   - `StatusCode != 200` 时把 body 包进 error（GLM.go:99）✓——很多人只判状态码不读 body，线上出问题只能瞎猜
   - `len(Choices) == 0` 防越界 ✓
   - 错误路径统一 `%w` 包装 ✓

4. **`image_scaling.go` 的 multipart 是手工组装的。**
   用 `CreatePart` + `textproto.MIMEHeader` + `FormDataContentType`，而不是找现成 helper，说明 multipart 格式是真看懂了。这部分面试可以讲。

5. **循环里的错误路由方向对。**
   工具不存在（loop.go:74）、工具执行失败（loop.go:79）都转成 Observation 回喂模型而不是直接 `return err` 终止。这是 ReAct 自愈的关键，第一版能写成这样说明理解了协议。

6. **值/指针接收者的选择有意识。**
   Echo 无状态用值接收者；ImageScaling 有状态用指针 + 构造函数注入 client。

### 1.3 A 档：真 bug（会崩 / 会死循环）

#### A1. `GLM.go:86-87` 漏检查 error 就解引用

```go
req, err := http.NewRequestWithContext(ctx, http.MethodPost, endpoint, bytes.NewReader(data))
req.Header.Set("Content-Type", "application/json")   // err 没判，req 出错时是 nil → panic
```

`image_scaling.go:96` 同一件事写对了（判了 err）。两处不一致，改回来一行的事。

#### A2. `parse.go` 的解析过于脆弱（已用等价逻辑实测）

用与 `parse.go` 完全等价的逻辑跑样例，结果：

```
"Action: echo"                → ToolName="echo"    ✓
"**Action**: echo"            → ToolName=""        ✗ markdown 加粗不认
"Action：echo"（全角冒号）    → ToolName=""        ✗
"Final Answer：你好"（全角）  → FinalAnswer=""     ✗
"Action Input:" 换行接值       → Input=""           ✗ 跨行不认
"Thought: 我直接回答\n答案42"  → 全空                ✗ 完全不守格式
```

第 3、4 条最要命：提示词是中文，GLM 是中文模型，输出全角冒号 `：` 的概率不低。
一出现 → `ToolName=""` → 走"工具不存在"分支 → 白烧到 `maxLoop` 耗尽 → 整个 `Run` 返回错误。

修法：
- 归一化：全角 `：`→`:`；去掉 key 前后的 `` ` `` `*` `**`；key 比较忽略大小写
- `Action Input` 支持跨行：从冒号后取到下一个 key 行之前
- 兜底：既没解析到 Action 也没解析到 Final Answer 时，回喂一条"格式不符合要求，请重新按 Thought/Action/Action Input 输出"的 Observation，而不是 `工具 "" 不存在`。后者模型看不懂。

#### A3. `loop.go:34` map 遍历顺序随机

`buildPrompt` 里 `for _, t := range a.tools` 遍历 map，每次进程启动工具清单顺序都可能不同。
现在只有 echo 看不出来；到 8-10 个工具时提示词每轮不稳定，影响可复现性，也没法给提示词做缓存。
→ 按 name 排序再输出。

#### A4. 响应体没有大小上限

`GLM.go:94` 和 `image_scaling.go:110` 的 `io.ReadAll` 都是裸读。异常或恶意服务端返回超大 body 就能打爆内存。
→ 包一层 `io.LimitReader`。

#### A5. 工具参数没有边界校验（对"护栏"叙事最重要的一条）

`image_scaling` 的 `imgPath` 完全来自 LLM 生成的文本：
- `os.Open` 能读进程权限内任意文件（`/etc/passwd`）
- `os.WriteFile` 能覆盖任意路径

计划里本来就有"护栏"这一层——这就是第一个真实落点，不是理论问题。
→ 限定根目录 + `filepath.Clean` + 校验 Clean 后仍在前缀内。

### 1.4 B 档：设计上值得改

- **B1. `IsFinal()` 用 `FinalAnswer != ""` 判断。** 模型输出空的 `Final Answer:` 就变成 false，然后拿 `ToolName=""` 去查表绕圈。应区分"没解析到任何字段"和"解析到了但内容为空"。
- **B2. 循环耗尽的错误不带上下文（loop.go:84）。** 把最后一条 assistant 回复带上，排查效率差一个量级。
- **B3. 全项目零日志。** `Run` 中间过程完全不可见——看不到发出去的 messages、模型原文、每轮耗时。规划里"trace + 成本台账"是卖点，现在就该用 `log/slog` 每轮打 Action/Input/耗时。另外 `glmResponse` 里的 `usage` 字段被丢掉了，token 数白扔。
- **B4. `main.go:18/28` 用 panic 收尾。** CLI 里打一屏堆栈很难看 → `fmt.Fprintln(os.Stderr, ...)` + `os.Exit(1)`。另外 `question` 硬编码，接交互要看 `os.Args` / `bufio.Scanner`。
- **B5. 429 限流无重试；`endpoint`/`model` 是包级 const，不可配置。** 评审必问点。
- **B6. `echo.Execute` 忽略 ctx**，没做 `ctx.Err()` 检查（小事，工具多了值得统一）。

## 2.2 计划的问题（按重要性排序）

### 问题 1（最严重）：层 B 与 agenthub 之间没有真实的调用关系链

agenthub 是单进程 CLI agent，3 个工具，跑在笔记本上。它：
- 不需要服务发现——没有多实例
- 不需要消息队列——没有异步任务
- 不需要 JWT——没有多用户

面试官一问"你为什么用 etcd"，如果答案是"为了简历上写 etcd"，**比不写还糟**。计划把这些列进"缓做"，说明 glm 自己也虚。

**改法（两条路，选一条）**

路线甲：给层 B 每个组件建一条"因为 agent 真的需要"的理由链，串不起来的删掉。可行的最小闭环：
```
agent 每轮产生 trace  →  上报到一个独立的可观测性服务（gin + MySQL：task / step / token / 成本）
                      →  服务提供查询接口（"这个任务几轮、花了多少钱"）
```
这一条链就够撑起"后端"叙事了，而且是真的被 agent 调用的。etcd / 服务发现只有在"agent 多副本 + 工具服务多实例"的情境下才有理由——那就得先造出那个情境（Docker Compose 起两份）。

路线乙：把后端层的承载体从 agenthub 换成 image-processor / 比价服务的集群化——它们本来就是 HTTP 服务，多实例、要限流、要扩缩。这样是"两个项目各讲一层"，而不是硬把两层塞进一个项目。对面试更清楚，也更省力。

### 问题 2：MVP 排序把最能体现工程能力的东西放最后，而它们改造的是内核

②③ 本质是同一个模式重复（struct + 构造函数 + Description + Execute），信息量低、耗时长——②已经花了 3 天还没完工。
而 ④（trace / 成本 / 护栏）才是区分"写过 agent demo"和"做过 agent 系统"的东西，恰好是面试官最爱问、最少有人做的。

**更关键**：trace 和护栏是**横切关注点（cross-cutting concern）**。现在 `Run` 里 `Chat` 和 `Execute` 都是裸调用，没有任何 hook 点。第 4 周再回头加，要重构 `Run` 的结构、签名，还要动所有工具的调用路径。**越晚引入，改动越大。**

**改法**：把"可观测性 + 护栏"整体提到 ④ 之前，并且现在就定好扩展点（见问题 3）。

### 问题 3：计划里没有预留任何 hook 点 / 中间件概念

建议现在就定两个接口，各 5-10 行，默认实现 no-op，第 ④ 周只填实现、不动内核：

```go
// 可观测性：挂在 Run 的三个位置
type Observer interface {
    OnLLMCall(ctx context.Context, messages []llm.Message, reply string, d time.Duration)
    OnToolCall(ctx context.Context, name, input, observation string, err error, d time.Duration)
    OnStep(ctx context.Context, step int)
}

// 护栏：三处检查
type Guard interface {
    CheckInput(userInput string) error          // 用户 / 外部输入
    CheckToolArgs(name, input string) error     // 模型生成的工具参数（对应 A5）
    CheckObservation(name, observation string) error // 工具返回内容，防注入
}
```

`Run` 里各插一个调用点。默认 no-op 实现。A5 那个"工具能读任意文件"的问题，落到 `CheckToolArgs` 里正好。

**这是整份复盘里最值钱的一条：先定扩展点，再定实现。**

### 问题 4：RAG 选型与项目主题错位，计划没回答"检索什么、为什么用向量"

计划写"RAG = chromadb，embedding 边车复用 law:8001"（那是法律项目的 bge 模型）。但电商决策里：

- **商品筛选 / 比价是结构化条件匹配，用向量检索是错配。** 价格区间、品牌、品类这些条件应该走 SQL / WHERE 链——你在实习项目里做的三层匹配（品类 SQL 锁定 + 子品类 canonical 化 + FilterIntent 多条件 WHERE 链）正是对的做法。
- 向量检索真正有理由的落点是**非结构化文本**：商品评价、退换货政策、售后规则、FAQ。

**改法**：把 RAG 收窄成"一个工具"（agent 自己决定何时调），检索对象明确为评价 / 政策 / FAQ 的语义问答；商品筛选继续走结构化。
另注意复用边界：三层匹配的代码属于实习项目，能不能搬进个人仓库要先确认——要么重写一版精简的，要么只用思路不用代码。

### 问题 5：计划内部自相矛盾——MCP 还挂着，但 9-08 已得出"MCP 场景不匹配"的结论

计划文本写着"MCP 官方 go-sdk"，而 9-08 会话里你自己推出来的结论是：两端都在你手里、同语言 → 编译期接口直调是最短路径，MCP 只会多一层 SDK + JSON-RPC + 进程拓扑。这种残留会在面试时自己打自己。

**改法**：删掉，或改成一句明确的可辩护定位：
> "MCP 作为可选适配层，仅在有第三方 / 跨语言工具接入需求时再加——实现 Tool 接口插入工具表即可，内核零改动。"

当装饰挂着是负分。

### 问题 6：每一步没有可验证的验收标准

①的验收是"成功返回了"——主观，不可复现。没有数字就写不进简历，也没法回答"你怎么知道它变好了"。

**改法**：每步定硬指标

| 步骤 | 验收标准 |
|---|---|
| ① | 端到端跑通 **+ `Run` 四条路径各有单测**（正常 Final / 工具不存在 / 工具失败 / maxLoop 耗尽） |
| ② | **换工具时 loop.go 零改动**（glm 已提过这条，很好，保留）+ 一次真实缩放产出的文件路径 |
| ③ | 比价工具在 N 条样本上的正确率 ≥ x% |
| ④ | trace 能回答"这次任务几轮、每步耗时、花了多少 token / 多少钱" |

### 问题 7：缺"评测集"这一环

agent 项目最容易被问"你怎么知道它变好了"，计划里完全没有评测。
**改法**：最小评测——15~20 条任务，每条带期望结果（期望的工具调用序列 或 期望答案的关键点），写个小脚本或 `go test` 打分。成本一天，收益极大。**这是 agenthub 从"demo"变成"project"的门槛。**

### 问题 8：maxLoop 是魔法数字，且计划和实现不一致

9-07 定的设计是 N=10，现在 `main.go` 写的是 5，两个数都没有理由。
而且真正的护栏是**预算**（token / 钱花完就停），不只是轮数。
**改法**：maxLoop 提到 10（多工具协作 + 重试余量），同时加 token 预算（比如单任务 20k）——这正好也是成本台账的输入端。

### 问题 9：目标岗位与产出物错位——主攻 Go 后端，但计划重心在 agent

简历 11 月中冻结，寒假投"后端 / agent"。层 B 被列为"缓做"，结果很可能是：agent 做得很深，但缺后端证据（并发 / QPS / 存储设计 / 部署 / 一致性）——而后端岗问的正是这些。

**改法**：做一张"证据矩阵"，每个岗位要求映射到一个可验证的项目证据：

| 岗位要的东西 | 现有可用的证据 |
|---|---|
| 高并发 IO / 资源控制 | image-processor（自研内存池 + 信号量限流，已集成） |
| 部署运维 / 线上排障 | goblog（VPS + systemd + nginx，已上线） |
| 数据建模 / SQL | 比价三层匹配 + trace 落库的表设计 |
| LLM 工程 / agent 架构 | agenthub |
| 可观测性 / 成本治理 | agenthub 的 trace + 成本台账 |

# 2.4 最终决策（2026-09-10，Hermes 定）

## 决策原则：什么叫"经得起拷打"

面试官读一个简历项目只有三层路径，项目必须在这三层都不掉链子：

```
第 1 层（5 分钟）：README → 架构图 → 一段真实的运行输出 → 有测试吗
第 2 层（15 分钟）：读内核（loop.go / trace 链路）→ 看 commit 历史
第 3 层（20 分钟）：挑一个点往死里问 —— 只在你要"展开讲"的那个话题上
```

由此推出三条硬标准，每条决策都要过这三关：

1. **为什么需要它**——没有它会怎样？答不上来的东西一律删掉。
2. **你怎么知道它对**——有数字、有测试、有评测，不靠"我跑通了"。
3. **踩过什么坑**——具体到现象和根因。面试官判断真假靠这个。

一句话：**砍到每个技术选型都能用一句话说清"为什么需要它"。**

---

## 决策 1：后端层只做一条真链路，其余全砍

**砍掉**：etcd / 服务发现、Redis Stream、JWT + Redis 鉴权、监控、熔断。
不是"缓做"，是**砍掉**。理由：agenthub 是单进程 CLI agent、3 个工具、单用户——这些组件在现有拓扑下不存在成立的理由。

> 这句话本身就是加分项。面试被问"你怎么没上服务发现/消息队列"，答案是：
> "我评估过，当前拓扑下服务发现和 MQ 都不成立——单实例无需注册发现，无异步任务无需队列。加了只是为了简历好看，那反而是减分。"

**新做（层 B 的唯一承载体）**：trace 服务 + agent 侧上报，形成真实的两进程 HTTP 调用链。

```
┌─ agenthub 进程 ────────────────┐        ┌─ traceserver 进程 ──────────────┐
│  Run() 每轮                     │  HTTP  │  gin                             │
│   ├─ Observer.OnLLMCall ────────┼───────►│  POST /api/traces   （批量上报） │
│   └─ Observer.OnToolCall ───────┼───────►│  GET  /api/tasks/:id （明细）    │
│  reporter: channel + worker     │        │  GET  /api/stats     （聚合成本）│
│  批量 flush / 失败重试 / 幂等键 │        │         ↓ gorm                   │
└─────────────────────────────────┘        │      MySQL                       │
                                           └──────────────────────────────────┘
```

**形态决策**：同一个 repo，`cmd/` 下两个入口（`cmd/agenthub`、`cmd/traceserver`）。
理由：一次 `git clone` + `docker compose up` 就能跑全系统 → README 好写、面试官好复现 →"一个系统两层叙事"在目录结构上就看得见。

**技术栈**：trace 服务用 gin + gorm + MySQL（符合你既有偏好）。Agent 层保持零依赖手写——两层用不同工具，且各有理由，这本身是可以讲的点。

**为什么这条链路是"后端面试地形"**：这条链上全是能追问到底的硬话题——

| 环节 | 会被追问什么 |
|---|---|
| 异步上报 | 为什么不在 Run 里同步上报？（阻塞内核 / 放大延迟） |
| channel + worker | 缓冲区满了怎么办？（丢弃 + 计数，不能阻塞内核） |
| 批量 flush | 为什么批量？多长时间 / 多少条触发？进程退出时丢数据怎么办？ |
| 失败重试 | 退避策略？重试会不会重复写库？ |
| 幂等 | 幂等键怎么设计？（task_id + step_no 唯一索引，INSERT ... ON DUPLICATE KEY） |
| 表设计 | 为什么拆 tasks / steps 两张表？索引建在哪？ |
| 聚合查询 | "这个月花了多少钱"这条 SQL 怎么写？走不走索引？ |
| 成本 | token 怎么算钱？价格表放哪？ |

**表结构（建议）**

```sql
tasks  (id, question, final_answer, status, total_tokens, cost_yuan, created_at)
steps  (id, task_id, step_no, thought, action, action_input,
        observation, latency_ms, err, created_at)
      UNIQUE KEY uk_task_step (task_id, step_no)   -- 幂等键
```

**验收**：跑一次任务，`GET /api/tasks/:id` 能看到每轮 Thought/Action/Observation + 耗时；`GET /api/stats` 能回答"这次任务几轮、花了多少 token、多少钱"。

## 决策 2：工具层全自己做，不搬实习代码

**比价工具**：不搬实习项目那套三层匹配。自己建一张 `products` 表（几百条 mock 数据：name / category / brand / price / color / stock）+ 一个 SQL 查询工具。
理由：① 实习代码能不能搬进个人仓库本身有边界问题；② 自己写的小版本更好讲，且直接给你"数据建模 + SQL"的后端证据；③ 几百条数据用 SQL 是**对的**，这正好和 RAG 形成对照。

**RAG**：**不引 chromadb**，Go 手写。
- 检索对象收窄到**非结构化文本**：商品评价 / 退换货政策 / 售后 FAQ（200 条左右）
- embedding 调智谱的 embedding 接口（复用同一个 key；若控制台没有或太贵，退回你本地的 law:8001 边车）
- 检索 = 内存里存 []float32 + 暴力 cosine 排序

> 面试回答："200 条政策文本，暴力算 cosine 是毫秒级，上向量数据库是过度设计。数据量到十万级、或需要持久化和增量更新时再引入。"
> —— 和你 MCP 那段的结论同源：**知道一个流行技术什么时候不该用，比会用它更值钱。**

**商品筛选 vs 语义检索，两条路分清楚**：结构化条件（价格区间 / 品牌 / 品类）走 SQL；语义问题（"这款的退换货政策是什么"）走向量。这个对照本身就是一个能讲 5 分钟的设计点。
