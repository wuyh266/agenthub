# AgentHub 工程化项目计划

> 初次制定：2026-09-13  
> 最近修订：2026-09-15  
> 定位：基于 Go、MySQL 和 Redis 的异步 Agent 任务执行平台  
> 学习目标：通过一条完整链路掌握 Go 后端、Redis、Agent 运行机制和模型上下文控制。

---

## 1. 项目目标

AgentHub 接收用户任务，通过 Redis Streams 调度 Worker。Worker 运行 Agent，Agent 在预算内组织模型上下文并调用模型和工具，MySQL 保存任务状态、执行步骤和结果。系统需要处理排队、取消、重复消息、Worker 退出、模型限流和上下文超限，并用测试、故障实验和评测证明行为。

电商决策作为主要业务场景，现有图片处理服务作为第一个真实工具。

```text
用户或客户端
    ↓
AgentHub API
    ├── MySQL：任务、步骤、工具调用和结果
    └── Redis Streams：异步任务调度
              ↓
         Agent Worker
              ↓
        Agent Runtime
          ├── Context Builder：组织本轮模型输入
          ├── 模型客户端
          ├── 图片处理工具
          ├── 商品查询工具
          └── 政策与 FAQ 检索工具
```

### 1.1 组件职责

| 组件 | 职责 |
|---|---|
| AgentHub API | 提交、查询和取消任务 |
| MySQL | 保存任务状态、完整执行记录和结果 |
| Redis Streams | 传递待执行任务，协调 Worker 消费 |
| Redis | 在第二版承担共享限流和短期运行状态 |
| Worker | 领取任务、执行 Agent、保存结果和处理失败 |
| Agent Runtime | 控制模型调用、工具调用、轮数和总预算 |
| Context Builder | 根据预算选择、精简和组织模型输入 |
| Tool | 提供图片处理、商品查询和政策检索等能力 |

### 1.2 两种上下文

项目需要分别学习两种 context：

1. Go 的 `context.Context`：传递取消信号和截止时间，让 API、Worker、模型和工具一起停止。
2. 模型上下文：决定每次调用模型时发送哪些消息和工具结果，并控制单次输入 token、累计 token 和信息压缩。

## 5. 阶段 1：可测试、可观察的 Agent 内核

### 5.1 核心正确性

1. 修复 GLM 创建 HTTP 请求后未检查错误的问题。
2. 为 `Parse` 增加表驱动测试，覆盖标准输出、全角冒号、Markdown 装饰、跨行输入和答案、空字段、字段冲突及非法回复。
3. 使用 fake LLM 和 fake Tool 测试 `Agent.Run`：
   - 直接回答。
   - 工具调用后回答。
   - 工具不存在或失败后修正。
   - 模型失败。
   - context 取消。
   - 达到最大轮数。
4. 对工具清单排序，使提示词稳定。
5. 明确停止原因：正常完成、轮数耗尽、预算耗尽、用户取消、模型错误和系统错误。
6. 模型响应保留正文、usage 和 finish reason。
7. 限制模型响应体、工具错误响应体和上传文件大小。
8. 图片输入和输出限制在任务工作目录内。
9. 图片输出加入任务 ID 或调用 ID，避免并发覆盖。

### 5.2 上下文观测基线

这一阶段先观察，不做复杂压缩。每次模型调用记录：

- 轮数和消息总数。
- system、user、assistant、observation 各自的长度。
- 工具结果长度。
- prompt tokens、completion tokens 和累计 tokens。
- 模型耗时和 finish reason。

保存至少一条多轮任务记录，并回答：

- 第四轮包含哪些历史消息？
- 哪类内容消耗最多？
- 哪些内容重复？
- 用户最初的硬约束是否仍然清晰？

### 5.3 验收

- 核心路径可以离线测试。
- Go context 取消能传到模型和工具。
- 图片并发处理时结果互不覆盖。
- 每轮输入规模和 token 用量可查看。
- `go test ./...`、`go vet ./...` 和格式检查进入 CI。

## 6. 阶段 2：Redis Streams 最小闭环

### 6.1 目标

尽早接触 Redis。通过一个 Worker 跑通 Stream、消费者组、读取、pending 和确认。

### 6.2 API

```text
POST   /api/v1/tasks
GET    /api/v1/tasks/:id
GET    /api/v1/tasks/:id/steps
GET    /healthz
GET    /readyz
```

### 6.3 MySQL

V1 先使用三张表：

| 表 | 作用 |
|---|---|
| `tasks` | 输入、状态、结果、错误、预算和时间 |
| `task_steps` | 每轮模型调用和停止原因 |
| `tool_calls` | 工具、参数、结果摘要、耗时和错误 |

第一版状态：

```text
pending → queued → running → succeeded
                           ↘ failed
```

### 6.4 Redis 最小实现

```text
Stream: agenthub:tasks
Consumer Group: agent-workers
Consumer: worker-1
```

消息只保存 task ID 和创建时间，完整任务输入从 MySQL 读取。

执行链路：

1. API 保存任务到 MySQL。
2. API 将任务 ID 写入 Redis Stream。
3. Worker 通过消费者组读取。
4. Worker 将任务改为 running 并调用 Agent。
5. Worker保存步骤、工具调用和结果。
6. 数据库保存成功后确认消息。

阶段 2 接受“数据库写成功但 Redis 发布失败时需要人工补发”的已知限制，阶段 6 用 Outbox 解决。

### 6.5 实验和验收

- 查看 Stream 消息、消费者组和 consumer。
- 读取一条消息但不确认，观察 pending。
- 确认后再次观察 pending。
- 记录 Stream ID、consumer 和 delivery 次数变化。
- 能演示消息从新增、读取、pending 到确认的完整过程。
- 提交任务后立即得到 ID，随后能查询执行结果。

## 7. 阶段 3：多 Worker、取消和基础恢复

### 7.1 目标

学习两个 Worker 如何竞争、消息为什么重复、Worker 退出后如何恢复。

### 7.2 任务

- 状态扩展为 pending、queued、running、succeeded、failed、cancel_requested、cancelled。
- 两个 Worker 使用不同 consumer 名称。
- 使用 MySQL 条件更新竞争任务执行权。
- 保存结果后再确认消息。
- 重复消息先查询任务状态；已完成任务直接确认。
- 根据 idle time 和 delivery count 接管失联 Worker 的 pending 消息。
- 第一版只做有限次数的基础重试。
- 增加 `POST /api/v1/tasks/:id/cancel`。
- queued 任务取消后由 Worker 跳过。
- running 任务将取消信号传入 Go context。

### 7.3 故障实验

| 实验 | 验证目标 |
|---|---|
| Worker 领取消息后退出 | 消息是否留在 pending |
| 另一个 Worker 接管 | 是否能继续处理 |
| 结果入库后、ack 前退出 | 是否跳过已完成任务 |
| 同一 task ID 发布两次 | 是否避免重复执行 |
| 两个 Worker 同时竞争 | 是否只有一个获得执行权 |
| 运行中取消 | context 是否传到模型和工具 |

### 7.4 验收

- 两个 Worker 可以共同消费。
- Worker 退出后消息可以被接管。
- 已完成任务不会因重复消息再次执行。
- queued 和 running 任务都能取消。
- 能解释至少一次传递、业务幂等和副作用风险。

## 8. 阶段 4：模型上下文控制

### 8.1 三层信息

```text
完整执行记录
    用于排障、审计和回放，保存到 MySQL

结构化任务状态
    用户硬约束、已确认事实、候选项、未解决问题

本轮模型上下文
    从任务状态、最近消息和工具结果中选择
```

完整记录不需要每轮全部发送给模型。

### 8.2 工具结果精简

- 商品搜索只返回 Top K 和必要字段，详情通过 ID 再读。
- 政策检索返回片段、来源和文档 ID。
- 图片工具返回产物 ID、路径、尺寸和状态。
- 大段原始数据保存到数据库或文件，模型接收摘要和引用。
- 工具结果设置最大长度，超限时明确标记截断。

### 8.3 四种限制

1. 单次输入预算。
2. 预留输出预算。
3. 任务累计 token 或费用预算。
4. Agent 轮数限制。

预算不足时按顺序保留：

| 优先级 | 内容 | 处理 |
|---:|---|---|
| 1 | 系统规则和当前目标 | 必须保留 |
| 2 | 用户硬约束和已确认事实 | 结构化保存并保留来源 |
| 3 | 最近几轮交互 | 按窗口保留 |
| 4 | 当前决策相关的工具结果 | 精简后保留 |
| 5 | 较早历史和冗长原文 | 摘要或引用 |
| 6 | 重复和无关内容 | 删除 |

### 8.4 第一版 Context Builder

- 固定保留 system 和原始用户目标。
- 保存预算、用途和禁用条件等硬约束。
- 保留最近 N 轮。
- 较早工具结果只保留摘要和引用。
- 记录构建后各部分 token 占用。
- 超预算时明确报错或压缩，不能静默丢失关键信息。

V1 使用确定性规则，方便测试。模型自动摘要放入 V2。

### 8.5 测试和对照实验

必须验证：

- 多轮后用户预算和“必须、不能、不接受”等条件仍存在。
- 精简结果能追溯到原始数据。
- 预算不足时保留内容符合优先级。
- 同一输入和状态生成确定的上下文。
- 累计预算耗尽后停止调用模型。

对同一组多轮任务比较：

1. 完整追加历史。
2. 工具精简 + 结构化状态 + 最近窗口。

记录输入 token、约束保留率、任务成功率、工具重复调用次数、总模型调用次数和平均费用。

### 8.6 验收

- 每轮上下文组成和 token 占用可查看。
- 长工具结果不会直接占满上下文。
- 关键约束经过多轮仍保留。
- 单次预算和累计预算都生效。
- 有完整历史与受控上下文的对照数据。

## 10. 阶段 6：V2 后端与 Redis 深化

### 10.1 Transactional Outbox

```text
MySQL 事务：
    INSERT tasks
    INSERT outbox_events
提交

Publisher：
    查询未发布事件
    写入 Redis Stream
    标记事件已发布
```

Publisher 可能重复发布，因此 Worker 的幂等判断继续保留。

### 10.2 重试和死信

- 错误分为可重试、不可重试和结果未知。
- 可重试错误使用带抖动的指数退避。
- 超过最大次数后进入死信 Stream。
- 支持查询和人工重新提交。
- 有副作用的工具使用幂等键或结果查询。

### 10.3 Redis 共享限流

- 限制单位时间的模型请求数。
- 限制多 Worker 的模型并发量。
- 使用 Lua 保证检查和更新原子执行。
- 并发许可设置 TTL，并处理 Worker 退出。

### 10.4 Redis 运行状态

使用 `agenthub:task:<task_id>:runtime` 保存 worker、当前 step、当前 tool 和 heartbeat，并设置 TTL。MySQL 保存最终状态和完整历史。

### 10.5 上下文增强

- 使用模型生成较早历史的摘要。
- 摘要保留事实来源和版本。
- 必要时重新读取原始工具结果。
- 比较规则摘要与模型摘要的准确性、成本和延迟。

### 10.6 验收

- Redis 发布失败后 Outbox 自动补发。
- 重复事件不重复产生业务副作用。
- 多 Worker 总请求频率符合限制。
- Worker 退出不会永久占用并发许可。
- 死信任务可查询和重新提交。
- 自动摘要通过关键约束测试。

## 11. 阶段 7：结构化工具、电商场景和综合评测

### 11.1 结构化工具

逐步将字符串参数升级为带 JSON Schema 的工具定义和结构化 Tool Call。文本 ReAct 作为学习和兼容路径保留，主业务路径接入模型原生结构化工具调用。

### 11.2 业务工具

- `product_search`：用 SQL 按价格、品牌、类别和属性筛选。
- `policy_search`：检索退换货、保修、配送、售后政策和 FAQ。
- `image_scaling`：处理图片附件。

商品属性和价格使用 SQL；政策、FAQ 和评论使用语义检索。

### 11.3 对照评测

固定工作流基线：

```text
商品查询 → 政策查询 → 模型汇总
```

准备 20～30 条任务，覆盖无工具、单工具、多工具、参数缺失、工具失败、无结果、长工具结果、多轮硬约束和外部可疑指令。关键用例重复 3～5 次。

| 指标 | 目的 |
|---|---|
| 任务成功率 | 是否完成目标 |
| 工具和参数正确率 | 是否正确执行 |
| 依据正确率 | 是否与原始数据一致 |
| 约束保留率 | 多轮后是否保留硬约束 |
| 平均输入 token | 上下文控制效果 |
| 工具重复调用率 | 裁剪是否造成信息丢失 |
| P50/P95 延迟 | 端到端性能 |
| 平均费用 | 单任务成本 |
| 故障恢复率 | 故障后的完成能力 |

### 11.4 验收

- 回答能追溯到工具原始数据。
- 固定工作流和 Agent 有可重复的对照结果。
- 上下文策略有 token、约束保留率和成功率数据。
- 能说明 Agent 动态决策适用的任务类型。

## 14. 执行原则

1. 核心实现由项目作者亲自完成并能够解释。
2. 每次推进一个最小、可验证的闭环。
3. Redis 从正常消费开始，再学习 pending、接管、幂等、Outbox、Lua 和 TTL。
4. 上下文控制从观察开始，再做工具精简、预算、结构化状态和摘要。
5. 完整历史用于排障和回放，本轮上下文只携带当前决策所需的信息。
6. 每引入一个组件，都说明它解决的具体问题。
7. 正常路径完成后，验证超时、取消、重复、崩溃和依赖不可用。
8. 每个功能同时留下测试、文档和实验数据。
9. V1 完成并可展示后，再进入 V2。

最终工程链路：

> Go API 接收任务，MySQL 保存状态，Redis Streams 调度 Worker，Agent 在预算内组织上下文并调用模型和工具，系统处理取消、重复、超时和故障，最后用评测和压测证明结果。
